# api-contract-check

A service and its callers are built and deployed apart, so a contract change that compiles here can fail in another service, or in a Flutter app already installed on users' phones, which keeps the old code until each user updates. The check is: what the contract is, what changed, who reads it, and for each change whether it breaks them.

Rules that hold for every step:
- **Every verdict names its consumer and its reason.** A change is "breaking", "safe" or "unknown", never "probably fine".
- **A consumer you cannot see is unknown, not safe.** When callers live in repos you cannot read, say so and list what to check there.
- **Use the diff tools the repo already has.** Do not install new ones. A tool's verdict is reported with the command that produced it.
- Do not change the contract to make the check pass. Report, and let the user decide.

1. **Find the contract.** Look for the files that define it, and note which ones are generated:
   - REST: `openapi.yaml`/`.json`, `swagger.*`. A spec generated by springdoc or NestJS Swagger is often not committed; then the contract is the controllers and DTOs (`@GetMapping`, `@RequestBody`, `@JsonProperty`, Bean Validation; NestJS `@Get`, `@Body`, `@ApiProperty`, class-validator decorators).
   - gRPC: `*.proto`, `buf.yaml`. GraphQL: `*.graphql`, `schema.graphqls`, or code-first resolvers.
   - Messages: `*.avsc`, JSON Schema files, or the classes serialized to the topic; the topic names in config.
   - Shared libraries: a DTO or client module that other services import, and its published version.

2. **Find what changed.** Diff against the branch the change will merge into (usually `main`):

   ```
   git diff main...HEAD --stat
   git diff main...HEAD -- path/to/contract
   ```

   If the repo already has a contract diff tool, run it too, for example:

   ```
   buf breaking --against '.git#branch=main'
   oasdiff breaking old.yaml new.yaml              # or openapi-diff, if the build has it
   graphql-inspector diff old.graphql new.graphql
   ```

   Get the old spec with `git show main:path/to/openapi.yaml`, written to a scratch file outside the repo. If the spec is only generated, run the repo's own task that writes it on both commits, or read the diff of the controllers and DTOs.

3. **Mark each change.** For a reader of the contract:
   - **Breaking:** removing or renaming a field, endpoint, RPC, query or topic; changing a type or format (int to string, date format, number precision); making an optional field required, or a nullable one non-null; a new required request field or parameter; a changed URL, method or success status code; a changed default; removing an enum value; reusing or changing a protobuf field number.
   - **Usually safe:** adding an optional request field, a response field, an endpoint or an RPC. It still breaks a reader that rejects unknown fields: a plain Jackson `ObjectMapper` (Spring Boot's own turns this off), Pydantic with `extra="forbid"`, json_serializable with `disallowUnrecognizedKeys`.
   - **Adding an enum value** breaks readers that fail on unknown values: Jackson by default, json_serializable without `unknownEnumValue`, and exhaustive `switch` in Dart, Java or TypeScript. Mark it unknown until those are checked.
   - **Message schemas:** read the registry compatibility mode from the repo's config (`BACKWARD` is the registry default). Under `BACKWARD`, adding a field without a default breaks; under `FORWARD`, removing one without a default breaks. Renaming an Avro field needs an alias. If the build has a schema registry plugin with a compatibility test goal, run it.

4. **Find the consumers.** Search the repo, and every module of a monorepo, for the path, RPC, query, topic or class name:

   ```
   rg -n "/orders/|OrderResponse|orders\.created" --glob '!**/build/**'
   ```

   - Generated clients: OpenAPI generator output, protobuf stubs, GraphQL codegen. Name the file each is generated from and whether it is regenerated in the build.
   - Flutter apps: json_serializable or freezed models (`fromJson`, `@JsonKey`) and retrofit or dio clients (`@GET('/orders/{id}')`, `dio.get(`). A non-nullable model field without a default throws in `fromJson` when the field is missing or null. Shipped app versions keep the old models.
   - Callers in other repos, gateways and API consumers outside the company cannot be seen from here. List each one you know of or suspect, and what to check in it.

5. **Report.** One line per change:

   ```
   GET /orders/{id}: `total` int -> string | BREAKING | mobile app OrderModel.fromJson | parses `total` as int
   ```

   Then the commands run and their output, the consumers not checked and why, and, for each breaking change, the safe path if one exists (add the new field beside the old, deprecate, version the endpoint or topic). For writing contract tests, use the write-tests skill; for running the builds, the build-and-test skill.
